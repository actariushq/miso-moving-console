# 미소 이사 콘솔 설계서 v0.2 (moving-console)

작성 2026-09-30 · v0.2: 기존 miso-console(v25.4) 콜로그 방식 반영 · 대상: 가정이사(방문견적 + 미소방문 통합) · 스택: Vercel(Next.js) + Supabase

> 표시 규칙: **[확정]** Jackson이 정한 것 / **[제안]** 설계 제안, 확인 필요

---

## 0. 한 장 요약

| 모듈 | 누가 | 무엇을 관리 | 북극성 KPI |
|---|---|---|---|
| **AM · 신규 정착** | 온보딩 AM | 첫 충전 → 첫 계약 → 안정 정착까지 파트너 1곳씩 | 첫 계약 도달률 · 도달 일수 |
| **AM · 캐파 확대** | 성장 AM | 정착 파트너의 전체 캐파와 미소 투입 비중 | 미소 투입률 · 견적 참여율 |
| **예약콜** | 예약콜 담당 | 미소방문 오더의 방문 당일(D0)~D+5 고객 확정 | 예약콜 대상 오더 계약 전환율 |
| **활동 기록** | 전원 | 모든 스테이지 이동·콜·특이사항 (삭제 불가) | 누락률 0 |

설계 원칙
1. **기록이 곧 상태.** 스테이지는 사람이 드롭다운으로 바꾸고, 바뀌는 순간 DB 트리거가 로그를 남긴다. 로그 없이 상태만 바뀌는 경로를 두지 않는다.
2. **콜은 결과 없이 못 닫는다.** 콜 기록 저장 = 결과 + 다음 액션(날짜) 필수. 다음 액션이 없으면 "종료 사유" 필수.
3. **큐가 먼저, 리스트는 나중.** 각 담당자 첫 화면은 "오늘 해야 할 것"(SLA 초과·예약된 재통화) 순서 큐.
4. **원천 데이터는 읽기만.** 파트너·오더·견적 원천은 미소 운영 DB(Redash)에서 동기화, 콘솔은 그 위의 운영 레이어만 쓴다.

## 1. AM · 신규 정착 트랙 (New AM)

**진입 [확정]:** 첫 충전 발생 → 자동 생성, 온보딩 AM 배정
**목표 [확정]:** 계약 성공 경험을 만들 때까지 추적. 리뷰·평점 관리, 미성사 피드백, 격려

| 스테이지 | 코드 | 이 단계에서 할 일 | 다음 단계 이동 조건 | SLA [제안] |
|---|---|---|---|---|
| 첫 충전 · 배정 대기 | N0 | AM 배정, 웰컴콜 예약 | AM 배정 + 웰컴콜 완료 | 충전 후 24h 내 웰컴콜 |
| 프로필·리뷰 세팅 | N1 | 프로필 사진·소개문, 기존 리뷰 이관(벌크), 서비스 유형(방문견적/미소방문) 확인, 1초견적 설정, 가능 지역·일자 파악 | 체크리스트 5개 완료 | 3일 |
| 첫 견적 대기 | N2 | 영상 견적 참여 안내, 수동매칭 제안 | 견적 1건 이상 제출 (자동) | 7일 초과 시 위험 플래그 |
| 견적 제출 · 미성사 | N3 | 미선택 사유 피드백(가격·프로필·응답속도), 격려, 다음 견적 코칭 | 첫 계약 (자동) | 미성사 3건마다 피드백콜 |
| 첫 계약 성공 | N4 | 축하콜, 작업 전 주의사항 안내 | 첫 이사 완료 (자동) | — |
| 첫 리뷰 확보 | N5 | 고객 리뷰 요청 가이드, 평점 확인, 낮은 평점이면 원인 청취 | 리뷰 1건 + 평점 ≥ 4.5 | 이사 후 7일 |
| **졸업 → 캐파 확대** | N✓ | 성장 AM으로 이관 (인계 메모 필수) | [제안] 계약 2건 + 평점 ≥ 4.5 + 최근 14일 견적 활동 | — |

이탈 분기 (어느 스테이지에서든): **위험(N!)** = 14일 견적 0 · 잔액 소진 · 1초견적 OFF · 평점 < 4.0 → 재케어 큐. **이탈(NX)** = 연락두절 3회 / 본인 중단 의사 (사유 필수).

카드에 항상 보이는 값: 충전일 D+n, 현재 스테이지 체류일, 견적 제출 수 / 선택 수, 평점·리뷰 수, 잔액, 마지막 컨택, 다음 액션일.

## 2. AM · 캐파 확대 트랙 (Active AM)

**목표 [확정]:** 파트너 보유 캐파를 파악하고, 그중 미소 투입 비중을 압도적으로 높인다. 팀 수, 톤수별 차량, 인력 파악 → 주기적 투입 비중 확인 → 라포 형성

### 2-1. 캐파 모델

| 항목 | 입력 | 비고 |
|---|---|---|
| 팀 수 | AM 입력 | 동시 작업 가능한 팀 |
| 차량 | 톤수별 대수 (1t / 2.5t / 5t / 5t 이상 / 사다리차) | 톤수 목록은 [제안] |
| 인력 | 정규 / 일용 | |
| 팀당 일 처리 | 기본 1건 | 소형 팀은 2건 가능 |
| 월 가동일 | 기본 22일 | 손없는날·주말 보정은 2차 |
| 타 채널 비중 | 자체영업 / 타 플랫폼 / 미소 (%) | 콜로 청취, 자가 응답 |

- **월 캐파(건)** = 팀 수 × 팀당 일 처리 × 월 가동일
- **미소 투입률** = 미소 월 계약 건 ÷ 월 캐파 → 핵심 지표
- **견적 참여율** = 견적 제출 건 ÷ 받은 요청(영상 배포) 건 → 선행 지표
- **일 최대 견적 참여 · 견적 마감일** 기록 [확정: HubSpot 파이프라인 설계와 동일 항목]

### 2-2. 스테이지

| 스테이지 | 코드 | 정의 | 할 일 | 컨택 주기 [제안] |
|---|---|---|---|---|
| 캐파 미파악 | A1 | 졸업 직후 / 캐파 입력 없음 | 캐파 인터뷰 콜 | 이관 후 3일 내 |
| 캐파 파악 완료 | A2 | 캐파 입력됨, 목표 미설정 | 투입 목표 합의 (예: 월 8건) | 주 1회 |
| 투입 확대 중 | A3 | 목표 설정, 투입률 < 40% | 수동매칭, 1초견적 거리·평수 업셀, 마감일 연장 | 주 1회 (성수기 매일) |
| 핵심 파트너 | A4 | 투입률 ≥ 40% | 클레임 지원, 우선 매칭, 관계 유지 | 주 1회 |
| 이탈 위험 | A! | 참여율 전주 대비 50% 이상 하락 · 잔액 소진 · 평점 하락 | 원인 청취 → 복귀 | 즉시 |

투입률 구간(40%)과 주기는 [제안] — 시즌 모드(준비기·피크·비수기)에 따라 주기만 바뀌도록 설정값으로 둔다.

## 3. 예약콜 트랙 (미소방문 오더)

### 3-1. 오더 흐름 [확정]

`고객 요청 생성 → 플래너 방문(촬영) → 영상 배포 → 파트너 견적 제출(0~6) → 고객 노출(최대 4) → 파트너 확정`

### 3-2. 견적 노출 규칙 [확정]

| 제출 수 | 노출 | 숨김 |
|---|---|---|
| 0~4 | 전부 | 0 |
| 5 | 4 | 1 |
| 6 | 4 | 2 |

`노출 수 = min(제출 수, 4)`. 숨김 대상은 하위 파트너 — **순위 기준은 미결** (현재 운영 기준 확인 필요. 없으면 [제안] 평점 → 계약률 → 가격 적정성 순). 콘솔은 숨김 견적도 회색으로 보여줘서 예약콜 담당이 협상 근거로 쓸 수 있게 한다.

### 3-3. 예약콜 스테이지 (D0 = 플래너 방문일, 최대 D+5)

| 스테이지 | 코드 | 진입 | 할 일 |
|---|---|---|---|
| 견적 수집 중 | B0 | 방문 완료(D0) | 대기. 견적 0건으로 D0 18시 지나면 **공급 경고 → AM 수동매칭 요청** 자동 생성 |
| 콜 대상 | B1 | 노출 견적 ≥ 1 + 고객 미확정 + [제안] 노출 후 24h 경과 | 1차 아웃바운드 |
| 통화 · 고민 중 | B2 | 연결됨, 결정 보류 | 재통화 예약 (날짜·시간 필수), 망설임 사유 태그 |
| 부재 | B3 | 미연결 | 재시도 (하루 최대 [제안] 3회, 문자 병행) |
| 계약 확정 | B4 ✓ | 고객이 파트너 확정 (자동 감지 또는 수동) | 확정 파트너·금액 기록, 예약콜 기여 여부 |
| 이탈 | BX | 사유 필수: 타사 계약 / 가격 / 이사 취소·연기 / 직접 해결 / 기타 | 종료 |
| 기한 만료 | B⌛ | D+5 경과 미확정 | 자동 종료, 마지막 상태 보존 |

**망설임 사유 태그 [제안]:** 가격 높음 · 견적 편차 큼 · 파트너 신뢰 · 날짜 미정 · 가족 상의 · 타사 비교 중. → 월별로 모아 AM 피드백(미성사 파트너 코칭)과 연결.

### 3-4. 오더 카드에 보이는 값

D+n 배지, 방문 플래너, 제출/노출 견적 수, 최저가·최고가·편차, 고객 이사일(남은 일수), 콜 시도 횟수, 다음 콜 예약시각, 망설임 사유.

## 4. 콜·활동 기록 체계 (v0.2 — 기존 miso-console 방식 계승)

### 4-0. 기존 콘솔에서 확인한 것 (v25.4 기준)

| 기존 콘솔 방식 | 새 콘솔에서 |
|---|---|
| 콜·문자·반려·노트·스테이지 이동을 **`lead_events` 한 테이블**에 쌓고 `event_type`으로 구분 | 그대로 계승 → `activity_events` 단일 원장 |
| 콜 기록 = **① 연결 여부**(연결됨/부재중/결번/수신 거부/기타) → **② 결과**(진행/보류/실패) → 보류 사유·실패 유형 2단계 | 그대로 계승, 모듈(신규 정착·캐파 확대·예약콜)별로 결과·사유 사전만 다르게 |
| 메모는 **결과와 무관하게 항상 함께 저장** (v20.2 — 원래 실패 사유만 남기던 것을 사용자 요청으로 변경) | 계승 + 연결된 콜은 메모 필수로 강화 |
| `purpose`는 현재 스테이지에서 자동 결정(확인 콜, 서류 등록 확인·1차 독촉 …), `stage_at`에 **컨택 당시 스테이지** 저장 | 계승 + **콜 후 스테이지**(`stage_after`)도 같은 행에 저장 → "이 콜이 퍼널을 움직였나"를 조인 없이 집계 |
| 한 파트너의 여러 서비스 딜을 한 통화로 처리 → 딜 수만큼 행이 생겨 **콜 수 부풀림** 버그 → `call_group`으로 1통화 1건 집계 (v21.14) | 처음부터 `call_group` 필수. 집계는 항상 `count(distinct call_group)` |
| 동명이인에게 메모 오기록 → **파트너 ID 기준 저장**으로 수정 | 모든 기록의 키는 rfq-admin 파트너 ID / 오더 ID. 이름은 표시용만 |
| **부재 정책**: 3회째 부재 문자 · 같은 날 2회째 부재면 내일 10시 · 17시 전이면 2시간 뒤 · 누적 5회면 Lost(부재) 자동 | 계승 (파트너용). 예약콜은 D+5 창이 짧아 고객용 정책을 따로 둠 (4-3) |
| 결번 → Lost 자동 / 수신 거부 → 수신거부 목록 + DNC | 계승 |
| Lost 처리한 대상이 팔로업·시도 퍼널에 남던 문제 | 종료 상태는 **모든 큐에서 즉시 제외** (뷰 조건으로 강제) |
| 콜 로그 CSV가 최근 5,000행에서 잘리던 문제 | 원장 조회는 기간 기준 페이지네이션, 행 수 상한 없음 |
| AM 터치: D1·D2·D3·D7·D14·D21·D30 + 이벤트(첫 선택·48h 접촉 불명·남은 견적 ≤2), 콜마다 **상태 판정(A~E)·현장 의견 태그·처방 코드** 기록 | 신규 정착 트랙의 터치 케이던스로 편입 (4-4) |
| 연결된 콜에서 **타사 플랫폼 ROI**(플랫폼·월 매출·월 비용) 수집 | 캐파 확대 트랙의 "채널 비중" 입력으로 연결 (투입률 분모 보강) |
| 콜 로그 탭: 기간·담당·서비스·유형·결과·컨택 시 스테이지·이동 여부·팔로업 여부 필터, KPI(콜·연결률·스테이지 이동·접촉 유니크·팔로업 예약), 일자별 막대, 요일×시간 히트맵, 담당별 비교, AI 요약 | 같은 구성 + 모듈 필터 + 예약콜 전환 지표 추가 (4-5) |

### 4-1. 통합 원장 `activity_events`

한 행 = 한 사건. 콜은 `event_type='call'`, 문자 `sms`, 스테이지 이동 `stage`, 특이사항 `note`, 필드 변경 `field`, 동기화 감지 `system`.

| 필드 | 설명 |
|---|---|
| `subject` / `subject_id` | partner(파트너 ID) 또는 order(오더 ID) |
| `module` | am_new / am_active / booking |
| `call_group` | 같은 통화에 속한 행 묶음 (한 통화로 여러 대상 처리 시). 집계 단위 |
| `attempt_no` | 이 대상에 대한 몇 번째 콜인지 (회차) |
| `purpose` | 콜 목적 — 스테이지·터치 키에서 자동 제안, 수정 가능 |
| `touch_key` | AM 터치 케이던스 키 (D1, D7 …, EV_SELECTED …) |
| `connect` | connected / absent / dead / refuse / etc |
| `result` | go / hold / fail (연결됐을 때만) |
| `reason_code` / `reason_detail` | 보류 사유·실패 유형(1단계)과 세부(2단계) |
| `state_code` / `voc_tags` / `rx_code` | AM 상태 판정·현장 의견·처방 |
| `hesitation_tags` | 예약콜 고객 망설임 사유 |
| `memo` | 통화 메모 (연결된 콜은 필수) |
| `stage_at` / `stage_after` | 콜 당시 / 콜 직후 스테이지 |
| `next_action_at` / `next_action` | **📌 팔로업** 일시·내용 — 기존 콘솔의 팔로업과 같은 개념. 콜 저장 시 필수(없으면 `close_reason`), 부재 정책이 자동 제안하고 담당자가 바꿀 수 있음 |
| `auto_rule` | 부재 정책 등 자동 규칙이 적용됐으면 그 규칙 이름 |
| `actor_id`, `created_at` | 누가, 언제 |

INSERT만 허용. 정정은 `note(kind=correction)`로 새로 남김.

### 4-2. 콜 결과 사전 (모듈별)

**① 연결** — 공통: 연결됨 · 부재중 · 결번·없는 번호 · 수신 거부 · 기타

**② 결과 (연결됨일 때)**

| 모듈 | 🟢 진행 | 🟡 보류 → 사유 | 🔴 실패 → 유형 |
|---|---|---|---|
| 신규 정착 | 합의한 액션 있음 (프로필 마감, 견적가 조정, 재참여 등) | 통화 곤란·재통화 / 고민해본다 함 / 현장 작업 중 / 충전 여력 없음 | 미소 비중 축소 의사 / 타 플랫폼 전환 / 폐업·휴업 / 불만 — 전화 금지 요청 / 기타 |
| 캐파 확대 | 투입 확대 합의 (목표 건수·1초견적 범위·마감일) | 통화 곤란·재통화 / 성수기 이후 논의 / 팀 사정 확인 후 회신 | 투입 축소 의사 / 타 플랫폼 전환 / 불만 — 전화 금지 요청 / 기타 |
| 예약콜 | 확정 의사 — 파트너 선택 안내 | 고민 중 (+ 망설임 태그: 가격 높음·견적 편차 큼·파트너 신뢰·날짜 미정·가족 상의·타사 비교 중) | 타사 계약 / 가격 / 이사 취소·연기 / 직접 해결 / 기타 |

**결과가 스테이지를 움직이는 규칙** (자동 이동도 `stage` 행이 따로 남음, `auto_rule` 표시)

| 조건 | 신규 정착 | 캐파 확대 | 예약콜 |
|---|---|---|---|
| 부재 | 변동 없음 (누적 5회 → 정착 위험) | 누적 5회 → 이탈 위험 | → B3 부재 (누적 5회 → 이탈: 연락 불가) |
| 결번 | → 이탈 (결번) | → 이탈 위험 | → 이탈 (연락 불가) |
| 수신 거부 | → 이탈 + 수신거부 목록 | → 이탈 위험 + 수신거부 목록 | → 이탈 + 수신거부 목록 |
| 보류 | 변동 없음, 재통화 일정 필수 | 변동 없음, 재통화 일정 필수 | → B2 고민 중 |
| 실패 | → 이탈 (유형 기록) | → 이탈 위험 (유형 기록) | → 이탈 (사유 기록) |
| 진행 | 수동 이동 | 수동 이동 | B2 유지 + 3시간 뒤 확정 확인 콜 자동 예약 |

### 4-3. 부재 정책

| 규칙 | 파트너 (AM) [기존 콘솔 그대로] | 고객 (예약콜) [제안] |
|---|---|---|
| 다음 시도 | 17시 전 → 2시간 뒤 / 17시 이후 → 내일 10시 | 19시 전 → 2시간 뒤 / 이후 → 내일 10시 |
| 같은 날 한도 | 같은 날 2회째 부재 → 내일 10시 | 같은 날 3회째 부재 → 내일 10시 |
| 부재 문자 | 3회째 부재 시 부재 문자 발송 기록 | 2회째 부재 시 "견적 도착·비교 안내" 문자 |
| 자동 종료 | 누적 5회 → 위험 단계 (이탈 아님, 재케어 큐) | 누적 5회 → 이탈(연락 불가) |
| 기한 | — | 다음 시도가 D+5를 넘으면 D+5 18시로 당김 |

담당자는 자동으로 정해진 다음 시도 시각을 저장 전에 보고 바꿀 수 있다. 바꾸면 `auto_rule`에 "수동 조정"이 남는다.

### 4-4. AM 터치 케이던스 (신규 정착 트랙)

기존 콘솔의 D-터치를 그대로 쓴다. D0 = **첫 견적 참여일** (기존과 동일). 첫 견적 전(N0~N2)에는 웰컴콜·세팅 콜만.

| 키 | 터치 | 채널 | 필수 | 성공 기준 |
|---|---|---|---|---|
| W0 | 웰컴콜 (첫 충전 당일) | 전화 | ✓ | 서비스 유형·가능 지역·일정 확인 |
| D1 | 첫 참여 리뷰 | 전화 | ✓ | 프로필 마감 또는 액션 1개 합의 + 환불 제도 인지 |
| D2 | 선택 분기 체크 | 알림톡 (B는 콜) | | 전원 상태 판정 |
| D3 | 환불·신뢰 콜 | 전화 (B 필수) | | B 환불 접수 100% |
| D7 | 첫 주 결산 | 전화 | ✓ | 현장 의견 태그 기록 100% |
| D14 | 상태 기반 터치 | 🟡🔴만 콜 | | 처방 합의 |
| D21 | 재충전 사전 대화 | 전화 | ✓ | 재충전 의사 or 미충전 사유 1개 |
| D30 | 졸업 판정 | 전화 | ✓ | 졸업 사유 기록 → 캐파 확대 이관 또는 휴면 |
| ⚡ 첫 선택 | 당일 축하 + 방문 준비 안내 | 메시지 | ✓ | 당일 |
| ⚡ 48h 접촉 불명 | 환불 도와주기 착수 | 전화 | ✓ | 24h 내 |
| ⚡ 남은 견적 ≤ 2 | 재충전 대화 | 전화 | ✓ | 다음 영업일 |
| ⚡ 미성사 3건 [신규] | 견적가·프로필 피드백 | 전화 | ✓ | 피드백 1개 전달 |

**상태 판정 (A~E, 기존 명칭 그대로)**: A 순항 중 · B 🚨 연결 실패(선택 후 48h 고객 미통화) · C 참여 중·성과 없음 · D 참여 끊김 · E 크레딧 소진 임박
**현장 의견 태그**: 가격경쟁 심함 · 요청 품질 불신 · 앱·절차 어려움 · 정산·환불 불만 · 물량 부족 · 기타
**처방 코드**: 견적가 조정 · 프로필 완성 · 재참여 유도 · 환불 대행 · 재충전 대화 · 방문 준비 지원 · 기대치 맞추기 · 기타

캐파 확대 트랙은 D-터치 대신 **주간 점검(WK)** 한 종류: 이번 주 가용 팀 수, 미소 투입 예정 건수, 타사 플랫폼 ROI 갱신, 상태(확대 중/유지/축소).

### 4-5. 콜 로그 화면과 집계 규칙

- **콜 수** = `count(distinct call_group)` where `event_type='call'`
- **연결률** = 연결된 콜 ÷ 콜
- **스테이지 이동** = `stage_after ≠ stage_at`인 콜 수, **연결 대비 이동률**도 함께
- **접촉 대상** = 유니크 `subject_id`
- **팔로업 예약** = `next_action_at`이 있는 콜
- **예약콜 기여 전환** = 예약콜 1회 이상 연결된 오더 중 B4 확정 비율 (콜 안 한 오더 확정률과 나란히)
- 화면: 필터 한 줄(기간·모듈·담당·연결·결과·이동 여부·메모 있는 콜만·검색) → KPI → 일자별 막대(연결/부재/실패) + 요일×시간 연결률 히트맵 → 담당별 비교 → 원장 표(시각·담당·대상·회차·모듈·목적·연결/결과·컨택 시 스테이지 → 콜 후·메모·다음 액션)
- 파트너·오더 상세의 **활동 이력 맨 위에 최근 콜 메모 3건**을 고정 표시 (기존 건의: 콜 진행 화면에 안 들어가도 이전 컨택 확인)

- **스테이지 자동 이동**: 동기화 잡이 조건 충족 시 이동 (N2→N3 견적 제출, N3→N4 계약 등). 사람 이동과 동일하게 로그

## 7. 미결 사항 (결정 필요)

1. **HubSpot과의 관계.** 파트너 콜·케어 기록을 HubSpot에 모두 남기기로 한 방침과 이 콘솔이 겹친다. (a) 콘솔이 원장, HubSpot은 요약 싱크 (b) HubSpot이 원장, 콘솔은 뷰 (c) 콘솔로 이전 — 중 선택 필요. 시안은 (a) 가정.
2. **숨김 견적 순위 기준** — 현재 5·6개 중 누구를 빼는지 운영 로직 확인.
3. **졸업 기준** (N → A) — 계약 1건? 2건? 평점 조건?
4. **투입률 구간·컨택 주기** 수치.
5. **예약콜 시작 시점** — 견적 노출 후 몇 시간 미선택이면 콜 대상인가.
6. **Supabase 프로젝트** — 신규 vs 콜 코치와 공유.
7. **방문견적(파트너 직접 방문) 오더도 예약콜 대상인지** — 시안은 미소방문만.
8. **기존 miso-console과의 경계** — 기존 콘솔에 AM 탭(D-터치)이 이미 있다. [제안] 인입~첫 충전(온보딩)은 기존 콘솔, 첫 충전 이후(신규 정착·캐파 확대)와 예약콜은 새 콘솔로 나누고, 첫 충전 시점에 기존 콘솔 이력을 읽기 전용으로 가져온다. 기존 AM 탭은 이관 후 닫을지 결정 필요.
9. **Supabase 공유 여부** — 기존 콘솔 DB(`lead_events`)를 같은 프로젝트에서 읽을지(이력 연속성↑), 새 프로젝트 + 첫 충전 시 복사할지.
10. **터치 D0 기준** — 기존처럼 첫 견적 참여일인지, 첫 충전일인지 (시안은 기존 방식)
11. **예약콜 부재 정책 수치** (4-3의 [제안] 칸)
